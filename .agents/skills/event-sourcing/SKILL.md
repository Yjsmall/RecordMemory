# Event Sourcing

把业务事实保存为可重放的事件，让当前状态及其来源能够被解释和重建。依据 [Martin Fowler 的文章](https://martinfowler.com/eaaDev/EventSourcing.html)，同时遵守本项目已经确定的范围。

## 使用范围与参考资料

- 设计或修改本项目持久化、录音恢复、AI 任务或记忆历史时，先读 [核心业务事件溯源方案](../../../docs/architecture/event-sourcing.md) 的相关部分；这是具体事件信封、事务、删除和恢复策略的维护位置。
- 核对原文含义，或处理历史查询、事件纠正、外部结果与代码演进时，读 [Fowler 原则与适配说明](references/fowler-principles.md)。其中明确区分原文和项目选择。
- 涉及功能范围时核对 [需求分析](../../../docs/requirements-analysis.md)。用户已经选择录音、AI 处理、记忆变更采用事件溯源，不反复要求重新选型，也不扩展到所有设置和 UI 状态。

事件溯源的关键是状态变化能由历史事件重建。只有操作日志、事件总线或 `SharedFlow.emit()`，不能证明系统满足这一点。也不因采用事件溯源就增加 Kafka、独立事件服务器、多个数据库或完整 CQRS 框架。

## 从真实写入路径开始

根据当前请求选择设计、实现或评审，不把每次使用变成全项目改造。

查明相关业务状态、写入入口、查询投影、内容存储和外部调用；特别检查页面、录音服务、小组件、通知、Worker 和导入恢复是否绕过同一业务入口。没有工程时产出具体方案，不把文档中的 API 当成现有代码。

本项目以业务事件及其保留的内容版本为事实来源，Room 查询表是可重建投影。核心状态不允许先直接改查询表，再尽力补写一条日志；操作租约、调度信息、普通设置和临时 UI 状态不因此都变成业务事件。

## 建模与处理边界

- 区分命令与事实：`StartRecording` 表示请求，只有实际采集开始后才能记 `RecordingStarted`；文件确实可用后才记 `RecordingSaved`。事件名称表达业务含义，避免只剩通用字段变更。
- 明确聚合边界和业务约束。聚合版本只解决同一对象的并发写入；“全应用只有一个采集会话”还需要跨入口的会话协调，不能只给每条录音加一个版本号。
- 建议以纯函数 `decide(state, command, inputs) -> events` 处理新命令，`evolve(state, event) -> state` 处理既有事实；时间、ID 和外部结果作为输入。不要在 reducer 内联网、读当前时钟、生成随机值或操作麦克风。
- 重放已经成立的事实，不能把历史事件重新当成新命令跑当前校验或重新执行 AI。对历史结构的兼容读取和对新命令的业务校验分别处理。
- 按聚合版本与本地日志位置处理顺序。`occurredAt` 与 `recordedAt` 用于表达不同时间含义，手机时钟和 UUID 排序不能替代并发控制。遇到迟到事件先确定业务语义，不直接把历史日志按发生时间重排。

事件信封、幂等键、`expectedVersion` 与唯一约束采用项目方案。正常修改追加事实或补偿事件；升级读取用明确版本转换。不要通过偷偷覆盖旧事件或只改投影来实现“撤销”。确需清除敏感内容时，按明确的删除策略处理，并说明可重建范围的变化。

## 正常处理与重放隔离

| 入口 | 应做的工作 | 副作用边界 |
| --- | --- | --- |
| 新业务命令 | 校验状态和版本，追加事件、更新核心投影，按需登记 outbox | 在同一 Room 事务内保存执行意图，提交后才调度外部工作 |
| AI／外部结果回写 | 保存结果版本，核对来源版本、尝试身份、取消／删除状态，再提交结果事件 | 重复结果不重复落库，迟到结果不覆盖人工编辑 |
| 投影重建／历史查询 | 从兼容的事件和已保存结果计算状态，维护投影检查点 | 不调用 AI、启动录音、发送通知或创建可执行 outbox 任务 |

优先让纯重放路径根本不持有网络、调度器或采集接口。已有系统若使用 Gateway 隔离副作用，显式区分执行上下文；不要用可被并发 Worker／协程互相覆盖的全局 `isReplaying` 开关。

处理外部查询时，保留足够重现业务判断的历史结果及来源版本。对本项目 AI，模型名、提示词和温度不足以重现输出，必须保存实际输出。重放遇到缺失结果，应报告缺失、损坏或合法删除；不能回退为一次新的付费请求。

Room 提交与 WorkManager 入队不具备共同事务。使用持久化 outbox 及恢复扫描弥补中间崩溃窗口，配合幂等、租约和尝试标识；不在数据库事务中等待网络。数据库去重不能保证服务端只处理一次或只计费一次。

## 本项目的恢复与内容约束

- 录音是用户触发的原生麦克风前台服务，不交给普通后台队列启动。历史 `RecordingStarted` 不证明当前仍在采集；重建后结合真实服务与文件情况校正中断状态。
- 文件和数据库不能一起原子提交。先完成音频／结果内容的可靠发布，再提交引用事件；为两者间的崩溃窗口保留核对恢复路径。不能仅靠数据库回放恢复未完成封装的音频。
- 区分进程重启、投影重建与备份导入。进程重启可调度仍获准执行的本机任务；投影重建不新建可执行任务；导入的未完成 AI 任务持久化为待恢复，用户继续后才执行，不能只改变页面显示。
- 事件引用独立正文版本；API Key 不进入事件。彻底删除覆盖历史正文、音频、投影、索引、快照及待执行任务，重放识别最小删除标记。无法访问的旧备份不会随本机删除自动清除。

## 历史、快照与演进

按请求选择所需能力，不默认实现多条时间线、任意逆运算或双时态系统。

- 历史查询先说明是“当时已记录的事实”还是“后来纠正后的当时状态”。按日志前缀重放支持前者；后者需要纠正与生效时间规则，不能仅过滤时间戳声称已支持。
- 用户纠正或撤销用有来源关联的新事件表达。逆向处理需要差量或旧值；无法逆算时从有效快照或初始状态正向重放。撤销数据库状态并不能撤销已经发生的外部效果。
- 查询使用当前投影，避免每次 Compose 重组都重放完整日志。确有成本问题再加入快照，记录其聚合位置和模型版本；快照必须可丢弃，重建发布要有一致边界，不能让界面读取半完成状态。
- 分别管理 Room 表结构、事件结构、投影算法和按时间生效的业务规则。修复投影 bug 与改变历史规则含义是不同操作；保存需要追溯的规则／配置版本，未知事件版本不得静默跳过后宣称恢复完整。

## 有针对性的验证与交付

实现或修改核心逻辑时，按所改路径选择有意义的验证：

- 实时投影与相同历史重建一致；对网络、录音、通知和任务调度使用会在被调用时失败的替身，确认重放无副作用。
- 重复命令、重复结果与两个并发旧版本写入不会产生重复内容或静默覆盖。
- 在事务提交／任务入队、文件发布／事件登记等边界模拟退出，验证可恢复状态。
- 原文编辑、取消或删除后到达的 AI 结果不覆盖当前内容；备份导入不自动上传。
- 变更涉及旧事件、快照或删除时，使用对应历史样例验证兼容、失效和内容不复活。

文档任务核对概念、边界和引用即可，不为此创建应用测试工程。评审指出具体写入路径、可重现后果与修复建议；实现交付说明实际改动、已运行验证及剩余限制，不把测试计划写成已通过的结果。
