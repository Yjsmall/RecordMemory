# Fowler 原则与项目适配

来源：[Martin Fowler, Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)。文章日期：2005-12-12；本次阅读：2026-10-09。页面说明该文仍为草稿，未持续更新。以下为原创归纳和适配说明，不复制原文全文或 C# 示例，也不把项目选择归为作者的强制规则。

## 原文如何影响设计

| 原文章节 | 关键观点 | 使用 skill 时的判断 |
| --- | --- | --- |
| How it Works | 状态变化由事件驱动；事件历史支持 Complete Rebuild、Temporal Query 和 Event Replay | 检查领域变化能否从事件恢复；有审计记录本身还不够 |
| Application State Storage | 每次从空状态算起可能很慢；当前状态可缓存，快照可减少重放成本 | 保留投影供日常读取，快照按需要增加，不能成为唯一保留的数据 |
| Structuring the Event Handler Logic | 事件处理选择逻辑和领域逻辑可分开；Transaction Script 与 Domain Model 都能采用 | 按复杂度选择组织方式，不强制每个事件类实现 `Process()` |
| Reversing Events | 差量容易逆算；设置绝对值通常需要先前值；从快照正向重放可替代逆操作 | 仅在需要逆向恢复时记录足够旧值；不要给所有事件机械添加 `undo()` |
| External Updates | 外部系统通常无法区分实时处理与回放，重复通知会产生真实后果；Gateway 可隔离 | 重建和历史查询关闭外部效果，隔离机制不侵入业务判断 |
| External Queries | 当前查询结果可能不同于历史结果；应能查询可信历史值或记录原查询结果 | 持久化真正影响结果的外部输入；本项目回放直接读取已保存 AI 输出 |
| External Interaction | 同时返回结果并改变远端状态的调用结合了两类难题 | AI 生成既有不可重现输出，也可能产生任务与费用，不能当作普通无害查询 |
| Code Changes | 新功能、缺陷修复、随时间变化的业务规则需要区别处理 | 事件结构兼容并不等于规则语义兼容；历史纠正与重新解释要有明确版本和目标 |
| When to Use It | 历史追踪、复现调试、并行模型和追溯修正有收益，外部交互也增加复杂度 | 围绕已有需求实施；事件溯源不会自动带来所有历史能力或分布式同步 |

## 不要误归因给原文

**事实来源。** 原文讨论事件日志或当前应用状态作为 system of record 的两种安排。它不是“只有事件日志能作为官方记录”的单一规范。本项目明确选择事件及其保留内容为核心业务事实来源，投影可重建。

**不可变事件。** 原文的反转示例会在处理时给事件添加先前状态，且讨论替换错误事件后的重处理。本项目选择持久化事件追加、显式补偿和版本化读取，避免原地改写既有业务事实。不能声称不可变 DTO、补偿命令或 upcaster 全部来自该文。

**Kotlin 组织方式。** 原文偏好的事件对象多态处理是当时示例的选择。Kotlin 的 sealed 事件类型、显式分派和纯 `decide`／`evolve` 同样可以实现事件驱动的状态变化；无需照搬 C# 类层次或全局 Registry。

**工程机制。** Room 同事务写入、outbox、乐观并发、幂等键、WorkManager、独立可删除正文和凭据保护是本项目的工程方案。CQRS、特定消息中间件或分布式服务不是文章要求。

## 回放与外部交互的落地区别

原文通过 Gateway 判断处理上下文，以避免回放发送外部通知。示例中的简单布尔开关用于讲解概念；并发 Android 服务与 Worker 不宜共享这样的可变全局标志。本项目让投影重放路径没有调用外部接口和任务调度的能力。

原文的查询示例在未找到旧查询时会建立新查询。对本应用的严格重放，这个分支不可直接照搬：缺少 AI 历史输出时应停止受影响对象的恢复或标明缺失，不能自行联网补齐、悄悄产生新结果或费用。

例如，某次转写保存为版本 T1，摘要任务返回 S1，用户后来把转写改成 T2：

- 重建历史应仍能识别 S1 来自 T1，并按后续事件恢复其过期或已替代状态。
- 使用当前配置对 T2 再调用模型属于新的业务请求，产生新任务和新结果。
- 即使模型、提示词和温度相同，也不能用再次生成的文本冒充 S1。

## 纠正与时间语义

录音发生时间与入库时间分开保存，既有日志顺序保持明确。问“昨天系统知道什么”可以按记录顺序的历史边界重建；问“根据今天的纠正，昨天实际是什么状态”需要额外的生效与纠正规则。

修正人物偏好是一条新的有来源事实，不等于改写过去所有记录。若请求真的要求 Retroactive Event 或双时态查询，先明确重算范围、旧规则、外部效果补偿与验证样例；不要因文章提到这些能力就默认实现。

## 保留与删除的边界

完整重建依赖历史及必要外部结果仍然可用。本项目还要求用户可以彻底删除敏感内容，因此使用可删除的独立正文及最小墓碑；重建得到的是与删除策略一致的状态，不能承诺恢复已清除的过去正文。

文章没有给出 Android 隐私删除、Keystore 或备份恢复的方案。这些要求按项目架构执行；不得用“事件不可变”为由取消用户已经要求的删除能力。
